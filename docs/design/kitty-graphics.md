# kitty 图片：pane 里的图片由 keepane 自己保存（设计稿）

状态：**已实现第 1–3 步，待验收**（2026-11-27，用户："默认开，改吧"）。和下面的提议不同的地方见第 11 节。原状态：提议（2026-11-27）。用户原话："keepane 本身不应该依赖任何 term"；"改吧，先写 kitty 图形设计稿"；"web 可以先不考虑"；"先不加 image crate"；图片懒加载、server 重启后还在（4.2、4.9）。

取代：[control-mode.md](control-mode.md)（控制模式，暂不做，原因见第 3 节）。

## 1. 目标

1. pane 里的程序（`ut view`、yazi、chafa、keepane 自己的 dashboard）用 kitty 图形协议画的图片，在 keepane 里也能显示。
2. 图片是 pane 状态的一部分，和文字一样保存在 keepane server 里：外层终端关掉再连回来，图片还在；滚动、分屏、历史、link 副本都照常。
3. keepane 不依赖任何终端：外层终端支持 kitty 就显示图片，不支持就退回到文字，pane 里的程序不用知道外面是哪种终端。

不在范围内：

- 手机网页（用户定：先不考虑）。`/api/screen` 里的图片格子先按第 4.6 节的文字退回显示。
- sixel、iTerm2 的图片协议（以后可选，第 9 节）。
- HTML 渲染（第 7 节）。

## 3. 相似问题和为什么不做控制模式

1. **kitty 的 Unicode 占位符**：kitty 设计它，本来就是给 tmux、vim 这类"中间层"用的。程序先发图片数据并建一个"虚拟放置"（`U=1`），再往屏幕里写占位符字符。中间层只要把占位符当普通文字存下来、搬过去。
2. **tmux**：没有实现 kitty 图片，只能透传（`allow-passthrough`）。3.4 起支持 sixel，自己存图片、自己重画。透传在分屏、滚动、重连时都会错位，keepane 不走这条路。
3. **UnifyTerm 的 `graphics.rs`**：连传统的放置（`a=T`）也先换成占位符再存进屏幕。keepane 照它做，两边行为一致。

控制模式（让 UnifyTerm 直接渲染 pane）暂不做：

- 它让 keepane 在这种模式下退成某一个终端的后端，违背"keepane 不依赖任何终端"。
- 图片只在 UnifyTerm 里有，快照重连后就丢了。
- 它独有的好处只剩两条：每个 pane 有原生滚动和选择、命令标记（OSC 133）。字体、连字、配色、透明度在普通 attach 下本来就是 UnifyTerm 画的。
- 每个 client 功能都要回答"控制模式下怎么办"，长期要维护两套界面。

## 4. 方案

### 4.1 一个共用的入口：所有 `vt100::Parser` 前面加一层

新类型（暂名 `Screen`）包住 `vt100::Parser`，所有 32 处都改用它，不在各处分别处理。原因：pane、link 副本、镜像会话必须得到同样的屏幕，只改一处就会出现"pane 里有图、副本里没有"。

`Screen::process(bytes)` 做三件事：

1. 用一个跨调用的小状态机找出 `ESC _ G … ESC \`（一段输出可能把一个序列切成两半，状态要留到下一次）。其他字节照旧交给 `vt100`。
2. 把图片数据交给 4.2 的图片表。
3. 遇到"放置"，把它换成占位符文字（4.3），交给 `vt100`。

**归一**：第 3 步换出来的文字，连同显式的编号、行数，写进日志里的字节（`PaneChange::Output`）。link 副本收到的是归一后的字节，不用自己再算行数，屏幕逐字节相同。图片数据本身不进日志：入口把发送图片的 APC 从字节里拿掉，日志里只记一条 `PaneChange::Image { id, hash, 宽, 高, 格式 }`（4.2）。

### 4.2 图片表：存在磁盘上，看到才读进内存（懒加载）

用户定（2026-11-27）："没有看到的时候……用占位符，不加载，等用户看到的时候再加载，移出视野后一段时间也从内存中清掉"；"server 重启后应该也在"。

分两层：磁盘上存全部，内存里只放正在看的。

**磁盘**：

- 每张收到的图片写一次到 `<sessions-dir>/images/<sha256>.<扩展名>`，按内容的哈希命名：同一张图显示两次只存一份。放在 sessions 目录，是因为 server 重启后的恢复（4.9）也读这里；临时 server 用自己的 `KEEPANE_SESSIONS_DIR`，互不干扰。
- 每个 pane 一张小表：编号 → (哈希, 格式, 像素宽高)。没给编号的（`ut view` 这种），入口在 pane 内分一个编号，从高位开始（`0xF00000` 起），避开程序自己用的编号。分好的编号写进归一后的字节。
- 磁盘上限默认 1 GiB（新选项 `image-disk-limit`）。超了先删最久没被看过的。被删的图片，它的格子按 4.6 显示成标签。
- 清理：每 10 分钟扫一次，删掉"活着的 pane 和保存的会话都不再引用"、且超过 1 小时的文件。保存的会话还引用的图片一律不删。

**内存**：

- 只放"某个连着的 client 现在看得到"的图片：`compose` 拼屏时顺手记下这一屏里出现的编号（pane 的当前屏幕，或者复制模式翻到的那段历史）。
- 一张图第一次被看到时从磁盘读进来。几 MiB 的文件读一次约几毫秒，翻页时感觉不到。
- 移出所有 client 的视野 60 秒后从内存丢掉，再看到时重新读。
- 刚收到、还没写完磁盘的图片留在内存里，写完再按上面的规则处理。
- 内存上限 256 MiB 只作保险：同时看得到的图片超过它时，最旧的先显示成标签。

**协议细节**：

- 认得的格式：`f=100`（PNG；UnifyTerm 还收 JPEG、GIF、WebP，keepane 原样存、原样转发）、`f=24`、`f=32`。
- 读像素宽高只看文件头（PNG 的 IHDR、JPEG 的 SOF、GIF、WebP），不解码整张图。
- 只支持 `t=d`（数据在序列里）。`t=f`、`t=t`、`t=s`（文件、临时文件、共享内存）回答错误：server 和外层终端可能不在同一台机器上，路径没有意义。
- 删除：`a=d`（`d=a/A/i/I`）从 pane 的小表里去掉编号。磁盘文件由上面的清理删除。
- 隐私：图片和会话文件放在一起，权限也一样，只有本用户能读。

### 4.3 格子：占位符

1. 放置（`a=T`、`a=p`）换成占位符：每行写 U+10EEEE 加两个组合符（行号、列号），前景色设成编号（24 位真彩色）。一格 10 字节，pane 的 22 字节、拼屏的 24 字节都放得下。
2. 行数：给了 `r` 用 `r`。没给时按图片像素宽高和格子的宽高比算。格子宽高比取最近一个连上的 client 报的值（4.4 第 1 步），没有就用 1:2。算出的行数写进归一后的字节，所以每个副本一样。
3. 行列最多 297（kitty 组合符表的长度），也不超过 pane 的大小。
4. 光标照 UnifyTerm 的 `graphics.rs` 移动（`C=1` 时不动），两边一致。
5. 程序自己写的占位符（`U=1` 的虚拟放置）本来就是文字，不用换，只要入口记下这次虚拟放置的行列数。
6. 占位符之后就是普通格子：滚动、进历史、被清屏擦掉、分屏时被裁，都不用新逻辑。

**要保护的地方**：改格子颜色的代码不能碰占位符的前景色，否则图片编号就错了。逐个检查 2 节表里列出的 `recolor`、`dim_rect`、复制模式和搜索高亮、选择反色，全仓搜 `style.fg` 的写入点，统一用一个 `is_placeholder(cell)` 判断跳过。`recolor` 只换 16 色编号，入口把编号统一写成真彩色，不会被它换掉，但仍加测试锁住。

### 4.4 发给外层终端（每个 client 各自做）

1. **探测**：client 启动时问外层终端：`ESC _ G i=31,s=1,v=1,a=q,t=d,f=24;AAAA ESC \`，后面跟 `ESC [ c`（DA1）。在 DA1 的回答之前收到 `OK`，就是支持 kitty。同时问格子像素大小（`ESC [ 16 t`）。client 的输入解析（`src/vtinput.rs`）要认得这两种回答。结果用新消息 `ClientMsg::Terminal { kitty, cell_px, program }` 告诉 server；`program` 是 client 所在环境的 `TERM_PROGRAM`，用来判断外层终端收不收非 PNG 的图片（第 10 节）。最多等 500 ms，超时就当作不支持。
2. **编号**：每个 client 一张表，(pane, 编号) → 发给这个终端的编号。外层终端的编号是整个窗口共用的，所以从一个随机的高位起分配，避开外层终端里别的程序（比如 attach 之前在同一个标签页里跑过的 `ut view`）用过的编号。
3. **先发图再发格子**：`diff` 写一个占位符格子之前，查这个 client 有没有收到过这张图。没有就先发 `a=t,i=N,q=2`（数据分块，每块 4096 字节），再发 `a=p,U=1,i=N,c=…,r=…`（虚拟放置），然后才写格子。格子的前景色在 `compose` 时换成这个 client 的编号。
4. **释放**：外层终端这边也懒加载。一张图移出这个 client 的视野 60 秒后，对它发 `a=d,d=I,i=N`，让终端也释放内存；再看到时按第 3 步重新发。client 断开，表跟着丢掉；重连的是新终端，从头发。
5. 一个 client 不支持 kitty，这几步全部跳过，走 4.6。

### 4.5 程序问"支不支持"

程序发 `a=q`：入口代替终端回答 `OK`（`q=1`、`q=2` 时按规定不答），经现有的 `responses` 写回 pane。所以 pane 里的程序总认为终端支持 kitty。外层终端不支持的情况由 4.6 处理，程序不用管。

### 4.6 外层终端不支持 kitty 时

占位符格子画成一个标签。图片左上角那格起写 `▧ 图片 640×480`（放不下就截短），其余格子画成空白，用暗色背景标出图片占的范围。不加依赖。

不加 `image` crate（用户定，2026-11-27），所以不画半格方块。以后要加，再单独定。

### 4.7 dashboard

dashboard 是 pane 里的一个程序。keepane 支持 kitty 后，它也按协议画图：

- 用虚拟放置（`U=1`）加自己写占位符。dashboard 每次重画的都是格子，这正是占位符适合的场景。
- 外层终端支不支持由 server 判断，dashboard 总是发 kitty。退回由 4.6 处理。
- 第一批：`[0]` Files 和群文件 `[4]` 的图片预览（现在是 `ut view --mode half`）、群聊里的图片附件。
- 只发 PNG：kitty、WezTerm、Ghostty 都只认 PNG。不加 `image` crate，dashboard 没法把 JPEG、WebP 转成 PNG，所以对非 PNG 的图片照旧调用 `ut view --mode half`。

### 4.8 决定

| 问题 | 结论 |
|---|---|
| 1. 默认开还是关 | 开（用户定）：`set -g kitty-graphics on`，可以关。关掉时 APC 照旧丢掉，`a=q` 不回答，和现在一样 |
| 2. 加不加 `image` crate | 不加（用户定） |
| 3. 上限 | 懒加载（用户定）：磁盘 1 GiB，内存只放看得到的，256 MiB 作保险（4.2） |
| 4. server 重启后图片还在吗 | 在（用户定），同样只读看得到的（4.9） |

### 4.9 server 重启、link 副本：都按哈希取

- **重启**：保存会话时，`SavedPane` 多存这个 pane 的小表（编号 → 哈希、格式、宽高）。保存的历史本来就带颜色（`pane_histories`，`src/server/mod.rs:2063`），占位符格子（字符、组合符、真彩色前景）跟着历史一起存下、一起恢复。恢复后小表也回来，图片按 4.2 的规则看到时才从磁盘读。要加测试确认保存历史时组合符和真彩色前景一个不丢。
- **link 副本**：日志里只有 `PaneChange::Image { id, hash, … }`，没有图片数据。副本看到某张图、本机磁盘上又没有时，发新消息 `ToServer::ImageWanted(hash)`，主机回 `ToClient::ImageData(hash, 数据)`，副本存进自己的磁盘。所以大图片不再挤占日志的 8 MiB，快照也不用带图片。
- 主机上找不到这个哈希（被清理了）：回"没有"，副本显示标签。

## 5. 面板和群聊能不能更好看

能，但只能"加图片"，不能"换成图片"。

能做的：

- 图片预览、群聊里的图片附件显示原图，不再是半格方块。
- 群聊里每个 agent 和人一个小头像（占 2×1 格）。
- `p` 的二维码画得更清楚，扫码更快。
- 以后可以画小图表（比如 agent 的 token 用量曲线），但要画图的依赖，先不做。

不该做的：

- 用图片画圆角气泡、渐变背景、特殊字体。这些要在每次改尺寸、换主题时重新生成图片；文字不能选中复制；不支持 kitty 的终端只看到标签。
- 规则：每个面板只用文字也必须完整可用，图片只是锦上添花。验收时用"外层终端不支持 kitty"的情况跑一遍每个面板。

布局照旧是格子，字体、配色、透明度照旧由外层终端决定。

## 7. HTML 渲染：不在范围

kitty 图形协议只能显示像素图片，不能排版 HTML。在终端里"渲染 HTML"只有两条路：

1. 转成文字（像 w3m、html2text）：不需要 kitty，现在就能做。markdown 已经有 `ut md`。
2. 用无头浏览器把网页截成图片再显示：要带一个 Chrome，慢，不能点击、不能选中文字。不建议。

要看真正的 HTML，用手机网页（web 端）或系统浏览器。

## 8. 香农六法

1. **简化**：先只做"`ut view a.png` 在支持 kitty 的终端里显示、滚动、重连后还在"。不做退回、不做 dashboard，就能验证整条链路：入口、图片表、占位符、按 client 发送。
2. **相似问题**：kitty 的占位符本来就为中间层设计；UnifyTerm 的 `graphics.rs` 已经把传统放置换成占位符。照搬这两者的做法。
3. **换说法**：不是"让 keepane 显示图片"，而是"让图片变成一种格子"。之后 keepane 已有的格子机制（滚动、历史、裁切、日志、副本）全部自动适用。
4. **推广**：同一个入口以后可以接 sixel（换成同样的占位符格子）；同一个"按 client 发送"可以接别的图片协议。
5. **结构分析**：入口和图片表（4.1–4.2）、格子（4.3）、按 client 发送（4.4）、退回（4.6）、dashboard（4.7），可以分开验收。
6. **逆向**：要"图片和文字一样可靠"，必须成立：所有 parser 走同一个入口；副本拿到归一后的字节；改颜色的代码不碰占位符；每个 client 先收图再收格子。第 4 节逐条对应。

## 9. 分步（每步单独验收、单独发版）

1. **入口、磁盘图片表、懒加载、占位符、按 client 发送**：`Screen` 包住所有 parser；`a=t/T/p/d/q`、`U=1`；图片写磁盘、看到才读、60 秒后丢；client 探测和 `ClientMsg::Terminal`；不支持 kitty 时画标签。e2e：pane 里发图，用一个"假 kitty 终端"当 client，检查收到的图片数据和格子；滚动、分屏、detach 再 attach 的屏幕逐字节相同；图片翻出视野 60 秒后内存里没有、外层终端收到删除，翻回来重新收到。
2. **重启和副本**：`SavedPane` 存小表，resume 后图片回来；`PaneChange::Image` 和 `ImageWanted`/`ImageData`，副本按哈希取；磁盘清理和 `image-disk-limit`。
3. **dashboard 用 kitty 画 PNG 预览**：`[0]` Files、群文件、群聊图片附件；非 PNG 照旧 `ut view --mode half`。
4. 以后可选：群聊头像；`image` crate（半格方块、JPEG 转 PNG）；sixel 输入；手机网页显示图片。

粗估工作量（没拆到函数级，误差可能 ±50%）：第 1 步约 1200–1800 行（含测试），第 2 步约 500–800 行，第 3 步约 300–500 行。

## 10. 风险

- **改颜色的代码破坏编号**：4.3 列出的检查和测试；全仓搜 `style.fg` 的写入点，一个都不漏。
- **磁盘越用越多**：`image-disk-limit` 默认 1 GiB 加定时清理（4.2）。清理绝不删保存的会话还引用的图片，要有测试锁住。
- **"看得到"算错**：`compose` 漏记一个编号，图片就会在还看得到时被丢掉，下一次重画才读回来，画面闪一下。测试覆盖：当前屏幕、复制模式翻历史、缩放（zoom）、弹窗盖住一部分。
- **外层终端编号冲突**：用随机高位起分配，冲突概率很小，但不是零。冲突时图片显示错，不影响文字。
- **探测失败**：有的终端既不答 `a=q` 也不答 DA1。最多等 500 ms 后当作不支持，attach 不会卡住。
- **非 PNG 数据转发给只认 PNG 的终端**：`ut view` 发的 JPEG 在 kitty 里会显示失败。server 看文件头，外层终端不是 UnifyTerm 时，非 PNG 的图片改按 4.6 退回。

## 11. 实现时和设计的不同（2026-11-27）

1. **入口只在本机 pane 的输出上**，没有给 32 处 `vt100::Parser` 都包一层（4.1）。原因：入口把发送图片的 APC 换成占位符文字（归一），日志、快照、link 副本、镜像会话拿到的都是归一后的字节，里面已经没有 APC，不需要再扫描。只有程序直接写进来的字节需要入口：`Pane::process_output`。
2. **server 内存里只放"正在发送"的图片**：一张图发给所有 client 之后就不再需要它的字节，60 秒没再取就丢掉；新的 client 连上时再从磁盘读（4.2 说的是"看得到时放在内存"，实际更省）。
3. **标签用英文** `▧ image 640×480`（keepane 界面的文字都是英文），宽度不够时截短。
4. **当作文字时是空白**：vendored `vt100` 的纯文本输出（`capture-pane`、复制模式、搜索、agent 读屏幕）跳过占位符格子（`Cell::is_image`）；带格式的 `capture-pane -e`（手机网页也用它）把每个占位符换成空格（`kitty::blank_placeholders`，第 9 轮验收发现）；只有保存的历史保留占位符，重启后靠它恢复。
5. **client 按环境变量判断外层终端**（`TERM_PROGRAM` 等，和 `ut view` 一样），没有向终端发 `a=q` 询问（4.4 第 1 步）。原因：Windows 的 client 用 `ReadConsoleInput` 读按键，终端的回答会变成一串按键事件，读回来不可靠。`ClientMsg::Terminal` 只告诉和 client 同版本的 server，旧 server 不认识这条消息。
6. **格子宽高比固定 1:2**（10×20 像素），没有向终端询问像素大小：理由同上。kitty 的虚拟放置会把图片按比例放进格子里，比例差一点只多一点空白，不会变形。
7. **保存的会话里图片表存成 `[编号, 图片]` 的列表**：JSON 的对象键只能是字符串，而 pane 是在带标签的 `SavedNode` 里读的，serde 在那里不会把字符串键读成数字（真程序测试 `restart-server` 时发现）。
8. **dashboard 的编号从 `0xE00000` 起**，避开程序自己用的小编号和 keepane 给无编号图片分的 `0xF00000` 起的编号。
9. **Windows 要新版 ConPTY**：Windows 自带的 conhost 会把 pane 里程序写的 APC 丢掉，图片到不了 keepane。微软的新版 ConPTY（`conpty.dll` 加 `OpenConsole.exe`，和 UnifyTerm 带的同一版 1.25）放在 `keepane.exe` 旁边时，`portable-pty` 会优先用它，图片能过去（实测：13 个 console 测试和 198 个 e2e 在新版下全部通过）。要不要随安装包带上，等用户定。
10. **`ut view` 要 UnifyTerm 那边改一处**才会在 keepane 里发 kitty 图片：它按 `TERM_PROGRAM` 选画法，现在对 `keepane` 选半格方块。keepane 在 pane 里设了 `KEEPANE_GRAPHICS=kitty` 给它判断。
11. **每个 pane 最多记 256 张图片**（`MOST_IMAGES`），超过时忘掉最早的；它的格子如果还在屏幕上，显示标签。
12. **发给副本的图片最多 8 MiB**（`link_feed::PICTURE_MOST`，订阅队列上限的一半）：再大的会把订阅挤断，副本重连后又要，反复断开（第 3 轮验收发现）。更大的回"没有"，副本显示标签；"没有"和哈希不对的回答都过 30 秒才再问。
13. **还不知道终端能不能显示图片时画空白**：client 连上后要过一会儿才送来 `Terminal`，先画标签会闪一下（第 1 轮验收发现）。
14. **收到后过 2 秒还有 pane 引用才写盘**（`images::SETTLE`），没人引用的立刻离开内存：UnifyTerm 的 `ut video` 用同一个编号每秒发约 30 帧，原来每帧都写一个文件、在内存里留 60 秒（第 7 轮验收发现）。保存会话之前，先把它引用的、还没写的图片写掉：图片要在磁盘上，只为了以后从保存的会话恢复，而每条恢复的路（`restart-server`、autosave、`save-session`、关机时保存）都先经过 `save_session_file`（改的时候真程序测试 `restart-server` 发现：原来想在 server 退出前写，可 `kill-server` 先关会话，退出时已经没人引用）。
15. **同一个 (pane, 编号) 在一个终端里只有一个编号**：新的一帧在这个编号下覆盖发送，终端里不会积压（第 7 轮验收发现）。
